---------------------------------------------------------------------
1. WHAT WE ARE BUILDING
---------------------------------------------------------------------
CHAKRA is a web app for predictive waste collection on a campus.
Every evening it forecasts each bin's chance of overflowing by the end of
tomorrow, selects only the bins that need a visit (plus reported, already
overflowing, and no-fresh-reading bins), plans capacity-safe vehicle
routes with a three-stage method (cluster -> assign vehicles -> order
stops with OR-Tools), lets workers confirm pickups on a phone, and proves
the trade-off on a 30-day digital-twin simulation.
Version 2 add-ons: M9 item classifier (one photo of one item), M10
overflow / missed-collection reports, M11 mess food-waste log with food
routes ending at a compost stop, and a cost estimate slide.
NOT in scope: hostel comparison view, segregation score, recycler handoff,
zone heatmap, marketplace, cameras, any LLM API, user accounts/login.

Modules: M0 Shared core (P2), M1 Simulator (P1), M2 Forecast (P1),
M3 Selection (P1), M4 Routing (P2), M5 Twin (P1), M6 Interfaces (P3),
M7 Handoff + badges (P3), M8 Scale lab (P2, stretch), M9 Classifier (P1),
M10 Reports (P2), M11 Mess log + compost (P3, stretch).
P4 = UI/UX polish, done by whoever is free (Section 16.5).

5. TIME, DATES AND THE SCENARIO CLOCK
---------------------------------------------------------------------
- Timezone: fixed offset UTC+05:30 via
  datetime.timezone(datetime.timedelta(hours=5, minutes=30)).
  Do NOT use zoneinfo (Windows lacks tz data without extra packages).
- All stored timestamps: ISO 8601 with offset, e.g. 2026-10-24T20:00:00+05:30
  Dates: YYYY-MM-DD.
- The seed writes these keys to table meta:
    scenario_date = the local date the seed was run (or --date)
    plan_date     = scenario_date + 1 day   ("tomorrow" in the app)
    scenario_now  = scenario_date at 20:30:00+05:30
    seed, created_at, data_label = "simulated"
- Live events (staff taps, reports, pickups, mess logs, item checks) are
  timestamped with the real current time in UTC+05:30.
- "Latest observation" of a bin = the row with the highest obs_id for that
  bin (NOT the latest timestamp).
- A bin is STALE if it has no observation, or its latest observation's
  observed_at is earlier than (scenario_now - 36 hours).
- The forecast horizon is the end of plan_date (23:59:59+05:30).

7. DATABASE SCHEMA  (backend/app/db.py creates it exactly; owner P2)
---------------------------------------------------------------------
Connection: sqlite3.connect(DB_PATH, timeout=10); row_factory = sqlite3.Row;
PRAGMA foreign_keys = ON; PRAGMA journal_mode = WAL.
One connection per request (FastAPI dependency get_db yields and closes).

CREATE TABLE IF NOT EXISTS meta (
  key TEXT PRIMARY KEY, value TEXT NOT NULL);

CREATE TABLE IF NOT EXISTS bins (
  bin_id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  group_type TEXT NOT NULL CHECK (group_type IN ('hostel','mess','department','mess_food')),
  group_name TEXT NOT NULL,
  stream TEXT NOT NULL CHECK (stream IN ('general','food')),
  lat REAL NOT NULL, lon REAL NOT NULL,
  capacity_l INTEGER NOT NULL CHECK (capacity_l > 0));

CREATE TABLE IF NOT EXISTS nodes (
  node_id TEXT PRIMARY KEY, name TEXT NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('depot','compost')),
  lat REAL NOT NULL, lon REAL NOT NULL);

CREATE TABLE IF NOT EXISTS vehicles (
  vehicle_id TEXT PRIMARY KEY, capacity_l INTEGER NOT NULL,
  fixed_cost_rs REAL NOT NULL, cost_per_km_rs REAL NOT NULL);

CREATE TABLE IF NOT EXISTS fill_observations (
  obs_id INTEGER PRIMARY KEY AUTOINCREMENT,
  bin_id TEXT NOT NULL REFERENCES bins(bin_id),
  observed_at TEXT NOT NULL,
  fill_pct REAL NOT NULL CHECK (fill_pct >= 0 AND fill_pct <= 100),
  source TEXT NOT NULL CHECK (source IN ('simulated','staff_tap','camera','pickup_reset')),
  quality TEXT NOT NULL DEFAULT 'ok' CHECK (quality IN ('ok','suspect')));
CREATE INDEX IF NOT EXISTS ix_obs_bin ON fill_observations(bin_id, obs_id);

CREATE TABLE IF NOT EXISTS fill_forecasts (
  forecast_id INTEGER PRIMARY KEY AUTOINCREMENT,
  bin_id TEXT NOT NULL REFERENCES bins(bin_id),
  created_at TEXT NOT NULL, plan_date TEXT NOT NULL, horizon_end TEXT NOT NULL,
  current_fill_pct REAL, predicted_increment_pct REAL, predicted_fill_pct REAL,
  p10_fill_pct REAL, p90_fill_pct REAL,
  p_overflow REAL CHECK (p_overflow IS NULL OR (p_overflow >= 0 AND p_overflow <= 1)),

CREATE TABLE IF NOT EXISTS plans (
  plan_id TEXT PRIMARY KEY, plan_date TEXT NOT NULL, tau REAL NOT NULL,
  created_at TEXT NOT NULL, chosen_fleet_size INTEGER,

  response_json TEXT NOT NULL);

CREATE TABLE IF NOT EXISTS route_plans (
  route_id TEXT PRIMARY KEY, plan_id TEXT NOT NULL REFERENCES plans(plan_id),
  fleet_size INTEGER NOT NULL, vehicle_id TEXT NOT NULL,

8. SYNTHETIC SCENARIO AND SIMULATOR RULES  (P1: app/sim/*)
---------------------------------------------------------------------
Layout (50 bins), defined in app/sim/scenario.py:
  Group names are real IIT Roorkee places; ids keep the old codes.
  Hostels (ids HA..HF): Rajendra, Rajiv, Radhakrishnan, Govind, Kasturba,
    Sarojini Bhawan: 5 bins each, HA-1..HA-5 ... HF-5, group_type hostel,
    stream general, capacity 240 L, name "Rajendra Bhawan bin 1".
  Messes (ids M1..M3): "Jawahar Bhawan Mess", "Cautley & Ganga Bhawan
    Mess", "Ravindra Bhawan Mess": per mess 2 general bins M1-G1, M1-G2
    (group_type mess, 660 L, name "Jawahar Bhawan Mess general bin 1") and
    2 food bins M1-F1, M1-F2 (group_type mess_food, stream food, 120 L,
    name "Jawahar Bhawan Mess food bin 1").
  Departments (ids D1..D4): "Civil Engineering Dept", "Electrical
    Engineering Dept", "Mechanical & Industrial Engg Dept", "Computer
    Science & Engg Dept": 2 bins each, D1-1, D1-2 ..., group_type
    department, 120 L, name "Civil Engineering Dept bin 1".
  Total 30 + 6 + 6 + 8 = 50.
  Positions (rng = numpy.random.default_rng(SEED)): each group centre is
  the building's position in OpenStreetMap (scenario.py); each bin is its
  group centre +/- uniform 0.0005 in lat and lon. Bin positions, fills and
  history are synthetic.
  Optional override: if backend/data/real_bins.csv exists (columns:
  bin_id,name,lat,lon) its values replace those bins' name/lat/lon.

Daily cycle for simulated day d:
  09:00  pickups decided from the 20:00 observation of day d-1 reset the
         true fill of those bins to 0
  09:00-20:00  the day's fill increment is added
  20:00  observation: observed = clip(round(true + Normal(0, 4)), 0, 100)
  overflow event = true fill >= 100 at 20:00
  true fill is capped at 130 (spill)
Daily increment (percent of capacity) for general bins:
  BASE_RATE_PCT = {"hostel": 22, "mess": 30, "department": 15}
  x WEEKDAY_FACTOR: hostel Sat/Sun 1.15; department Sat 0.4, Sun 0.2;
    mess Sat/Sun 0.9; all other days 1.0
  x EXAM_FACTOR during exam weeks: hostel 1.25, department 0.8, mess 1.0
    exam weeks (synthetic) = the 7 days starting scenario_date - 28 days,
    and the 7 days starting scenario_date + 14 days
  x bin multiplier, fixed per bin, uniform(0.6, 1.4)
  x daily noise exp(Normal(0, 0.25))
Food bins: increment comes from that day's mess logs:
  MEAL_BASE_KG = {"breakfast": 6, "lunch": 14, "snacks": 3, "dinner": 16}
  x mess multiplier uniform(0.8, 1.2) x exp(Normal(0, 0.2)) per meal
  split by category shares plate 0.5, kitchen_prep 0.3, unserved 0.2
  -> one log row per meal per category, weight rounded to 0.1 kg,
     weighed = 1 with probability 0.7, source 'simulated',
     logged_by 'simulated', created_at = date 20:00
  food litres = total_kg / FOOD_DENSITY_KG_PER_L, split equally over the
  mess's 2 food bins; increment pct = litres / capacity_l * 100
Missing readings: each bin-day observation is missing with probability
  0.02; additionally 2 fixed bins (chosen by rng) have their last 2 days of
  observations missing, so they are STALE in the demo.
History: 45 days ending on scenario_date (inclusive), run under
  history policy B: visit a bin the next morning if its observed fill > 70
  (or if the reading was missing for 2 days in a row). Each history pickup
  is stored in pickup_events with route_id 'HIST-<date>', completed_at
  <date>T09:00:00+05:30, collected_volume_l = true fill x capacity (capped
  at capacity), level NULL. History pickups do NOT create batches.
The seed (app/seed.py, owner P1) writes: meta, bins, nodes, vehicles (from
  config), fill_observations (source 'simulated'), pickup_events (history),
  mess_waste_logs (45 days). It does NOT write forecasts, plans or reports.

9. FORECAST, P(OVERFLOW) AND SELECTION RULES  (P1)
---------------------------------------------------------------------
Increment data (from observations + pickups):
  For a bin, take consecutive daily observations o(d-1), o(d) of sources
  simulated/staff_tap/camera. If a pickup happened between them, the
  observed increment is o(d); otherwise o(d) - o(d-1). Skip pairs where
  either value is 100 (censored) or a day is missing. 'pickup_reset' rows
  are reset markers, not data points.
Features for target day t: group_type (one-hot), weekday of t (0-6),
  is_weekend, exam_week flag, capacity_l, mean of the bin's last 7 valid
  increments, last valid increment, and for food bins the previous day's
  total mess-log kg of that mess (0 for other bins).
Model: scikit-learn GradientBoostingRegressor(loss="quantile", alpha=a,
  n_estimators=200, max_depth=3, learning_rate=0.05, random_state=0)
  trained three times, a = 0.1, 0.5, 0.9 -> inc_p10, inc_p50, inc_p90.
  Sort the three so p10 <= p50 <= p90; clip increments at >= 0.
Evaluation (time split, never random): the last 10 days of history are
  validation, earlier days training. Report MAE of inc_p50, MAE of the
  persistence baseline ("tomorrow's increment = last observed increment"),
  and coverage = share of validation targets inside [p10, p90].
  Then retrain on all history for live forecasts.
  model_version = "gbq-v1-" + scenario_date.
P(overflow):
  current = latest observed fill_pct (Section 5)
  sigma = max((inc_p90 - inc_p10) / 2.563, 1.0)
  z = (100 - (current + inc_p50)) / sigma
  p_overflow = 0.5 * math.erfc(z / math.sqrt(2))
  predicted_fill_pct = current + inc_p50 (may exceed 100; do not cap)
  p10_fill_pct = current + inc_p10, p90_fill_pct = current + inc_p90
  If the bin has no observation: current, predicted values and
  p_overflow are null.
Selection rule for each bin, first matching rule wins:
  1 overflowing_now  latest fill_pct >= 100                selected=1
  2 reported         an overflow report with status open
                     or in_plan exists for the bin          selected=1
  3 needs_review     the bin is STALE                       selected=1
  4 p_over_tau       p_overflow > tau                       selected=1
  5 below_tau        otherwise                              selected=0
  tau must satisfy TAU_MIN <= tau <= TAU_MAX, else HTTP 422.
Reason text (exact templates, Python f-strings):
  overflowing_now: f"Overflowing now (last reading {fill:.0f}%)"
  reported:        f"Reported {kind_text} by {role} - {status}"
                   kind_text = "overflow" or "missed pickup"
  needs_review:    "No fresh reading in 36 h - visit and tap a level"
  p_over_tau:      f"{p:.0%} chance of overflow tomorrow, above tau = {tau:.2f}"
  below_tau:       f"{p:.0%} chance of overflow tomorrow, below tau = {tau:.2f}"
Demand for a selected bin (litres):
  stale with no reading: capacity_l * STALE_DEMAND_PCT / 100
  otherwise: capacity_l * max(current, MIN_DEMAND_PCT) / 100
  Every demand is an estimate: demand_uncertain = true.
Summary: selected, skipped (below_tau count), needs_review, reported,
  overflowing_now, expected_overflows_skipped = round(sum of p_overflow
  over below_tau bins, 2).
Decisions computed by POST /api/decisions are NOT stored. They are stored
  only when a plan is committed (POST /api/routes/{plan_id}/choose).

10. ROUTING RULES  (P2: app/routing/*)
---------------------------------------------------------------------
Distances: haversine (Earth radius 6371.0 km) x DETOUR_FACTOR = road km.
  Integer metres for OR-Tools = round(road_km * 1000).
Minutes of a route = road_km / SPEED_KMPH * 60 + SERVICE_MIN_PER_BIN * stops.
Effective vehicle capacity = capacity_l * CAPACITY_BUFFER.
Streams: general stops and food stops never share a route.
  General routes: DEPOT -> stops -> DEPOT.  Food routes: DEPOT -> stops -> COMPOST.
Vehicles for fleet size k = the first k of VEHICLES (one route per vehicle).
  If food stops exist and k >= 2: the last vehicle serves food, the other
  k-1 serve general. If only one stream has stops: all k serve it.
  If k == 1 and both streams have stops: the vehicle serves general and
  every food stop is unassigned (alternative infeasible).
Stage 1 - cluster (per stream). n clusters: run stages 1-3 + gate + 3b
  for every n from ceil(stream demand / effective capacity) to the
  stream's vehicle count; keep the run with the fewest unassigned stops,
  then lowest cost, then lowest km (a stream may leave vehicles idle).
  Once every stop is served, stop at the first n that is not better.
  seeds: first seed = highest-demand stop; next seed = stop maximising
  (distance to nearest existing seed) x demand. Then up to 10 iterations:
  order stops by (distance to nearest centroid / demand) ascending; assign
  each to the nearest centroid whose cluster still has capacity; recompute
  centroids as demand-weighted mean lat/lon; stop when assignments do not
  change. Stops that fit nowhere are unassigned.
Stage 2 - assign vehicles: sort clusters by load (desc) and give them to
  that stream's vehicles in order. Then one refinement pass: move a stop to
  another cluster of the same stream if that lowers its distance to the
  cluster centroid and capacity still holds.
Stage 3 - order stops: OR-Tools single-vehicle routing per cluster with
  start node DEPOT and end node DEPOT or COMPOST.
    from ortools.constraint_solver import pywrapcp, routing_enums_pb2
    manager = pywrapcp.RoutingIndexManager(n_nodes, 1, [start], [end])
    first_solution_strategy = PATH_CHEAPEST_ARC
    fast=False: also GUIDED_LOCAL_SEARCH with time limit ORTOOLS_TIME_LIMIT_S
    fast=True : first solution only (used by the twin and the scale lab)
  If the OR-Tools import or solve fails, fall back to nearest-neighbour
  order and set "solver": "fallback_nearest_neighbor" on that route.
Feasibility gate (after stage 3): if a route exceeds SHIFT_MIN, move its
  stop with the largest removal saving to another same-stream route that
  has capacity and time; if none can take it, mark it unassigned.
Stage 3b - relocate (streams with <= 300 stops, up to 20 passes): move a
  stop to its cheapest insertion in another non-empty same-stream route
  when that lowers total km and keeps capacity and shift; then re-order
  each route with OR-Tools (first solution) and keep the shorter order.
  An alternative is feasible only if: every selected stop appears exactly
  once across routes or in unassigned_bin_ids, unassigned is empty, every
  load <= effective capacity, every route minutes <= SHIFT_MIN.
Cost of an alternative = (number of non-empty routes x fixed_cost_rs) +
  (total km x cost_per_km_rs).
Recommended alternative = the feasible one with lowest total_cost_rs,
  ties broken by lower total_km. null if none feasible.
Baseline = nearest neighbour without clustering, same stops, same stream
  rule, same fleet size as the recommended alternative (k=2 if none
  feasible), same capacity, shift and distance rules: from the start node,
  repeatedly go to the nearest unvisited stop of the stream that still
  fits capacity and shift, then go to the end node; next vehicle.

11. REPORTS, PICKUPS, BATCHES, MESS LOGS
---------------------------------------------------------------------
Reports (P2):
  verified = 1 if reporter_role in ('staff','supervisor') else 0.
  Merge: if the bin already has a report with status open or in_plan, do
  not insert; increment report_count, set updated_at, and set verified=1 if
  the new one is verified. Response says merged=true.
  Missed collection: when a report arrives, look at the bin's decision in
  the latest committed plan (plans.status='committed', newest created_at).
  If that decision had selected=0 and reason_code='below_tau', set
  missed=1 on it (once) and return missed_collection=true.
  Lifecycle: open -> in_plan (when a committed plan includes the bin)
  -> resolved (when a pickup of that bin is confirmed). open -> rejected
  (dispatcher, POST /api/reports/{id}/reject; only from open).
  Reports can only ADD stops; nothing removes a bin from a plan.
Pickups (P3):
  The bin must be in that route's ordered_bin_ids, else HTTP 400.
  A second confirmation for the same (route_id, bin_id) -> HTTP 409
  "Pickup already confirmed".
  collected_volume_l = LEVEL_PCT[level] x capacity / 100 if level given,
  else latest observed fill x capacity / 100 (estimate).
  On success, in one transaction: insert pickup_events row; insert a
  fill_observations row (fill_pct 0, source 'pickup_reset'); insert one
  batch_events row (stream = bin stream, destination 'compost_stop' for
  food else 'depot', status 'pending_handoff', source_pickup_ids
  "[<pickup_id>]", volume_l = collected volume); set that bin's open or
  in_plan reports to resolved.
  Compost arrival: POST /api/pickups/arrive-compost {route_id}. The route
  must have stream 'food' (else 400) and all its stops confirmed (else 409).
  Then its food batches change to status 'delivered_to_compost'.
  CHAKRA records delivery only; it never reports compost produced.
Mess logs (P3): mess_id must be an existing mess group_name (e.g. "Jawahar Bhawan Mess"),
  date defaults to today (UTC+05:30), weight_kg in (0, 500], source 'staff'.

12. DIGITAL TWIN RULES  (P1: app/twin/policies.py)
---------------------------------------------------------------------
- Runs fully in memory (no database). Same layout as the app (SEED 42),
  fill noise seeds = (11, 22, 33).
- Per seed: 45 warm-up days under history policy B, then train the
  forecast model on the warm-up history; then 30 evaluation days.
- Common random numbers: draw the evaluation increments and mess logs once
  per seed, and run every policy from the same starting state with them.
- Policies: A = visit every bin every day; B = observed fill > 70 or >= 100
  or stale; C(tau) = Section 9 selection rule without reports.
- Each day: decide from the 20:00 observation -> plan_routes(stops,
  fast=True) -> use the recommended alternative (if none, the alternative
  with the fewest unassigned stops; unassigned bins are not picked).
- All three policies use the SAME router, so the twin compares selection
  policies only. Routing gain vs nearest neighbour is shown separately.
- Outputs per seed and policy: km, route_minutes (sum), cost_rs,
  overflow_events (bin-days with true fill >= 100 at 20:00), pickups,
  bin_days. Sweep C over tau = 0.1, 0.2, ..., 0.9. Aggregate mean, min,
  max across seeds. Sensitivity: seed 11, policies A and C(0.5), detour
  factor 1.2, 1.3, 1.5.
- Cache file: backend/data/demo_cache/twin.json (committed to git).

13. ITEM CLASSIFIER RULES  (P1: ml/*, app/classifier/infer.py)
---------------------------------------------------------------------
Model classes (exact order): ["battery","metal","organic","other","paper","plastic"]
Folder-label normalisation: lowercase, spaces and hyphens -> "_".
Label map (normalised source folder name -> class):
  paper->paper, cardboard->paper, plastic->plastic, metal->metal,
  biological->organic, food_organics->organic, vegetation->organic,
  trash->other, miscellaneous_trash->other, textile_trash->other,
  clothes->other, shoes->other, glass->other, brown_glass->other,
  green_glass->other, white_glass->other, battery->battery,
  batteries->battery
  Unknown folder name -> stop with an error listing the unknown names;
  the human may pass --map name=class to extend the map.
Datasets (human downloads them; do not hard-code download URLs or slugs):
  "Garbage Classification (12 classes)" on Kaggle (main source),
  "RealWaste" (UCI Machine Learning Repository; CC BY-NC-SA 4.0),
  "TrashNet" (GitHub repository by Gary Thung; optional).
Training: mobilenet_v3_small(weights=MobileNet_V3_Small_Weights.DEFAULT),
  replace model.classifier[3] with nn.Linear(in_features, 6); input 224;
  ImageNet mean/std; class-weighted cross-entropy; AdamW lr 3e-4;
  8 epochs; batch 64; stratified 80/10/10 split (seed 0) of the training
  sources; holdout source for the shift test = RealWaste.
Saved file backend/data/model/item_classifier.pt = torch.save of a dict:
  {"state_dict", "classes", "arch": "mobilenet_v3_small", "img_size": 224,
   "mean", "std", "model_version"}  (plain types only, so
   torch.load(..., weights_only=True) works)
Report file backend/data/model/classifier_report.json with random_test,
  shift_test and (optional) campus_test: accuracy, per-class precision,
  recall, f1, support, confusion matrix, image counts. Numbers are only ever
  read from this file; never typed by hand.
Inference rules:
  confidence = softmax top-1 probability; top3 list.
  unsure = confidence < CLASSIFIER_CONFIDENCE_MIN -> suggested_bin null and
    the UI says "Unsure - ask staff".
  hazardous = predicted class is battery (regardless of confidence).
  SUGGESTED_BIN (placeholder campus bin names, replace with real ones):
    paper   -> "Dry waste - paper"
    plastic -> "Dry waste - plastic"
    metal   -> "Dry waste - metal"
    organic -> "Wet waste - food and organic"
    other   -> "Other / reject"
    battery -> "Hazardous - hand over for special pickup"
  If torch is not installed or the model file is missing, the endpoint
  returns HTTP 503 {"detail": "Classifier model not available"} and the
  rest of the app keeps working.
The classifier checks ONE item. It never feeds routing or selection.

17. HONESTY LABELS
---------------------------------------------------------------------
- Every page header shows badges: pages showing scenario data or twin
  results show SIMULATED; working features show IMPLEMENTED; anything not
  built (cameras, compost output, recycler) is only ever text marked PROPOSED.
- The UI never states measured savings, campus accuracy, recycled or
  composted kilograms. Savings are "simulated savings".
- Classifier accuracy shown in the UI is read from classifier_report.json
  and labelled with the test set it came from.
- Mess-log rows from the seed are labelled simulated; rows typed by staff
  are labelled staff.

18. GIT WORKFLOW
---------------------------------------------------------------------
- One GitHub repo "chakra", branch main. Everyone works on main because
  files are owned by exactly one person.
- Before starting a prompt: git pull --rebase
- After a prompt passes its checks:
    git add <only your files>
    git commit -m "P1: <short summary>"
    git pull --rebase
    git push
- Never "git add ." or "git add -A". Never force-push.
- Never commit backend/.venv, node_modules, *.db, uploads or model files.
  The trained model file is shared by the human through a drive link and
  copied to backend/data/model/.

19. ACCEPTANCE TESTS (definition of done)
---------------------------------------------------------------------
T1  current 20%, inc p10/p50/p90 = 30/40/50 (forecast 60%) -> below_tau
    at tau 0.5;  current 75%, inc 20/30/40 (forecast 105%) -> p_over_tau.  [P1]
T2  Changing tau changes only bins whose reason is p_over_tau/below_tau.  [P1]
T3  Stale or missing readings -> needs_review, selected.                  [P1]
T4  Every selected bin served exactly once or listed unassigned;
    capacity and shift hold; infeasible input lists unassigned bins.     [P2]
T5  Baseline uses the same stops, fleet size, capacity, distances.       [P2]
T6  Food and general never share a route; food routes end at COMPOST.    [P2]
T7  Choosing an infeasible alternative -> 409.                           [P2]
T8  A report on a below_tau bin of the committed plan -> missed=1 once;
    the next decide() selects it with reason_code 'reported';
    two reports on one bin -> one active report (merged);
    a rejected report adds nothing.                                       [P2]
T9  A confirmed pickup creates exactly one batch and one pickup_reset
    observation; a second confirmation -> 409.                           [P3]
T10 arrive-compost only for a fully confirmed food route; food batches
    become delivered_to_compost.                                         [P3]
T11 The dashboard never reports recycled or composted kilograms.         [P3]
T12 battery -> hazardous true; confidence below 0.6 -> unsure true and
    suggested_bin null (test with a fake model output).                  [P1]
T13 /api/classify returns 503 when the model file is missing.            [P1]
